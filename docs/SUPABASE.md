## Configuration and key boundaries

Backend SUPABASE_URL, SUPABASE_PUBLISHABLE_KEY, SUPABASE_SECRET_KEY are required. Legacy SUPABASE_ANON_KEY/SUPABASE_SERVICE_ROLE_KEY aliases remain supported. No secret belongs in a VITE_ variable. Browser uses only VITE_SUPABASE_URL/VITE_SUPABASE_PUBLISHABLE_KEY. Current non-JWT API keys go on apikey; user JWT goes on Authorization, legacy JWT keys retain compatibility. Secret/service-role operations bypass RLS, so verified user_id and explicit owner filters are mandatory. Table grants are checked separately from RLS. See [official key semantics](https://supabase.com/docs/guides/getting-started/api-keys) and [RLS documentation](https://supabase.com/docs/guides/database/postgres/row-level-security).

The client constructs request-local headers and does not hold a mutable user session. Provider timeout is finite(0,30] seconds, default10, no write retry. Auth outage returns503 and never bypasses auth. Error/log output excludes keys, tokens, provider bodies and disclosures.
