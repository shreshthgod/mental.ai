# MENTAL.AI — Supabase setup

Identity and screening storage live in Supabase. This is everything that needs
your accounts, in order. Nothing here needs a code change.

---

## 1. Create the project

1. <https://supabase.com/dashboard> → **New project**
2. Pick a name, a strong database password, and a region near your users.
3. Save the **project URL** and the keys from **Project Settings → API**:

| Key | Where | Who gets it |
|---|---|---|
| Project URL | Settings → API | both services |
| `publishable` key | Settings → API Keys | both services (public by design) |
| `secret` key | Settings → API Keys | **api service only** |

> If your project still uses the older key names, the service accepts
> `SUPABASE_SERVICE_ROLE_KEY` and `SUPABASE_ANON_KEY` as aliases. Prefer the new
> names.

---

## 2. Create the schema

The schema is in the repository — the repository is the source of truth, not the
dashboard.

**Option A — SQL editor (simplest)**

1. Dashboard → **SQL Editor** → **New query**
2. Paste the whole of `supabase/schema.sql`
3. **Run**

**Option B — CLI**

```bash
supabase link --project-ref <project-ref>
supabase db push
```

**Option C — psql**

```bash
psql "$SUPABASE_DB_URL" -f supabase/schema.sql
```

It creates `public.profiles` and `public.screenings`, their indexes and triggers,
and enables RLS with per-account policies. It is idempotent, so re-running is
safe.

Verify:

```sql
select tablename, rowsecurity from pg_tables
 where schemaname = 'public' and tablename in ('profiles','screenings');
-- both rows must show rowsecurity = true

select count(*) from pg_policies
 where schemaname = 'public' and tablename in ('profiles','screenings');
```

### Sensitive data, deliberately stored

`screenings.text` holds the participant's own words, which for this product is
mental-health disclosure. It is RLS-protected and reachable only by the owning
account, but it is still health-adjacent data in a cloud database. `schema.sql`
documents the three columns to drop if you would rather not retain it, and what
to change in `api/db.py` alongside.

## 3. Create the first account

There is no account configured in this repository any more.

1. Dashboard → **Authentication → Users** → **Add user** → **Create new user**
2. Set an email and password. Tick **Auto Confirm User** (otherwise the sign-in
   is refused until you confirm).
3. `handle_new_user()` fires and creates the `profiles` row automatically.

---

## 4. Google sign-in (optional, one-time)

### 4a. Google Cloud Console

1. <https://console.cloud.google.com> → create or select a project
2. **APIs & Services → OAuth consent screen**
   - User type: **External**
   - App name: `MENTAL.AI`
   - Add your support email, developer contact email
   - Add the scopes Supabase needs (the consent screen lists them itself)
3. **Credentials → Create Credentials → OAuth client ID**
   - Application type: **Web application**
   - Name: `MENTAL.AI`
   - **Authorized redirect URIs** — exactly one:

     ```
     https://<YOUR-PROJECT-REF>.supabase.co/auth/v1/callback
     ```

     Replace `<YOUR-PROJECT-REF>` with the ref from your project URL
     (`https://abcdefgh.supabase.co` → `abcdefgh`). This callback is generated by
     Supabase and is not configurable from Mental.ai.
   - **Authorized JavaScript origins**: add your app's origin, e.g.
     `https://mental-ai.vercel.app`
4. Copy the **Client ID** and **Client Secret**

### 4b. Supabase

1. Dashboard → **Authentication → Providers**
2. **Google** → enable
3. Paste the client ID and client secret
4. Optional: set **Skip nonce check**? Leave it off. Set the default
   `client_id` only if you want Google to preselect an account.

The client secret lives **only** in Supabase. It is never a `VITE_` variable,
never in `vercel.json`, and never in this repository.

### 4c. Redirect and site URLs

Dashboard → **Authentication → URL Configuration**

| Field | Value |
|---|---|
| Site URL | `https://mental-ai.vercel.app` |
| Redirect URLs (production) | `https://mental-ai.vercel.app/screen` |
| Redirect URLs (local) | `http://localhost:5173/screen` |

Mental.ai sends Google sign-in back to `<origin>/screen`, the authenticated
destination — the same place email sign-in lands. Add a `/**` entry only if you
want deep links such as `/screen?from=…` to be accepted.

If you enable **email confirmation**, add the same origins under
**Email → Redirect URLs**, otherwise new accounts will not be returned a session.

## 5. Environment variables

### Vercel → Project → Settings → Environment Variables

**web service — public**

| Variable | Secret | Value |
|---|---|---|
| `VITE_SUPABASE_URL` | no | project URL |
| `VITE_SUPABASE_PUBLISHABLE_KEY` | no | publishable key |

**api service — private**

| Variable | Secret | Value |
|---|---|---|
| `SUPABASE_URL` | no | project URL |
| `SUPABASE_SECRET_KEY` | **yes** | secret key |
| `SUPABASE_PUBLISHABLE_KEY` | no | publishable key |

Locally, the backend reads `.env` at the repository root and the frontend reads
`web/.env.local`. Both are gitignored; `.env.example` is the committed template.

Never create `VITE_SUPABASE_SECRET_KEY`. Anything prefixed `VITE_` is inlined
into the browser bundle.

## 7. Verify end to end

| Test | Expected |
|---|---|
| Sign in with email + password | lands on `/screen`, nav shows your name |
| `SELECT` from `screenings` after a screening | one row, `user_id` = your `auth.users.id` |
| Sign in with Google (first time) | `auth.users` row + exactly one `profiles` row |
| Sign in with Google (second time) | same account reused, still one `profiles` row |
| Cancel Google at the consent screen | returns to the panel, no error state |
| Reload while signed in | session restored, no re-login |
| `GET /api/screenings` with another account's token | empty |
| Sign out, reload | back at the entry panel |

### Account linking

Supabase links identities by verified email automatically: if `student@example.com`
first signs up with a password and later uses **Continue with Google** on the same
address, and the provider returns that email as verified, Supabase attaches the
Google identity to the existing user rather than creating a second one. The
`screening_history` and `profiles` rows stay attached. Mental.ai implements no
custom merging logic, so this behaviour is Supabase's and cannot be bypassed.

## Troubleshooting

| Symptom | Cause |
|---|---|
| `503 Authentication service unavailable` | a `SUPABASE_*` value is missing on the api service |
| `Invalid email or password` on correct credentials | wrong project, or the account is not confirmed |
| Google returns to the panel without a session | the redirect URL is not in Supabase's allow list, or email confirmation is on |
| `relation "public.screenings" does not exist` | `schema.sql` has not been run |
| History is empty after signing in | the browser's local history panel and the cloud history are separate stores; see below |

**Local history vs cloud history.** The screening history panel still reads the
per-browser list it always has. `/api/screenings` is the cloud copy and is
populated automatically by `/predict`; nothing reads it yet. Moving the panel over
is a deliberate follow-up, not something the migration did silently.
## Recovery snapshot migration

`supabase/migrations/20261008_authoritative_analysis.sql` adds nullable analysis_result JSONB and permits SQL NULL condition labels for unavailable models. Existing rows remain untouched, marked legacy_unassessed. Apply to the explicitly isolated test project first using the project's established SQL migration mechanism; no remote migration was run here.

The migration also raises the storage hard character bound to100000, matching the API's permitted maximum configuration while the API enforces its effective cap before inference/save. It does not truncate or rewrite existing disclosures. Fresh installations use updated schema.sql; existing installations require the additive migration because CREATE TABLE IF NOT EXISTS does not alter existing columns/constraints. Explicit service_role read/insert/delete grants support actual server calls, not an RLS protection claim. Apply/verify only in the isolated environment first.

PostgREST inserts request `Prefer: return=representation`. Only a returned record id confirms saved. Rejected writes report not_saved; network or incomplete acknowledgement after an attempt reports unconfirmed and is not automatically retried. Authoritative snapshot is the validated AnalysisResult core, including safety and raw versions/probabilities. Persistence acknowledgement itself is a separate transient response field. Owner filters remain mandatory because the server privileged key bypasses RLS. Real schema/RLS/network verification remains blocked on isolated project and pre-provisioned identities.
